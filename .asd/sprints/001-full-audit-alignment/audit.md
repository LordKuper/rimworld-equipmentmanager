### Nullable migration — measured cost (workstream 1 headline)

Flipping `-p:Nullable=enable` on a **clean rebuild** of the production csproj surfaces:

- **131 distinct file:line warnings / 300 total occurrences across 32 files.** (Init's "~148" was the distinct estimate; measured distinct = 131.)
- Breakdown by code: **CS8618 ×132** (uninitialized non-nullable field/property — dominant; mostly `IExposable` save/load fields populated by Scribe, plus the static reflection-delegate fields in `CombatExtendedHelper.cs`/weapon caches), **CS8604 ×82** (possible-null argument), **CS8625 ×42** (null literal → non-null), **CS8602 ×22** (deref of maybe-null), **CS8601 ×14** (possible-null assignment), **CS8603 ×4** (possible-null return), **CS9264 ×2** (non-null auto-prop, `ManageWeaponRulesDialog.cs:30`), **CS8619 ×2** (`IEnumerable<StatDef?>` vs `IEnumerable<StatDef>`, `WorkTypeRule.cs:118`).
- Hotspots (distinct warnings/file): `WorkTypeRule.cs` 36, `Loadout.cs` 30, `MeleeWeaponRule.cs` 20, `ToolRule.cs` 18, `RangedWeaponRule.cs` 18, `CombatExtendedHelper.cs` 16, `ManageWeaponRulesDialog.cs` 14, `EquipmentManagerGameComponent.cs` 14, `SkillWeight.cs` 10, `PawnCapacityWeight.cs` 10, `ItemRule.cs` 10. Remaining 21 files ≤8 each.
- **JetBrains annotation inventory to replace:** **224 nullability attributes** = 205 `[NotNull]` + 19 `[CanBeNull]`, plus **36 `using JetBrains.Annotations;`** lines (one per source file). Distinct from `[UsedImplicitly]` (×13) which is NOT a nullability attribute and stays (still needs the JetBrains `using` where referenced — do not blanket-remove the using).
- **C-1 [nullable-migration, critical]** Enable `Nullable enable` on `EquipmentManager.csproj` and resolve all 131 NRT sites green under `TreatWarningsAsErrors`. CS8618 fields are largely mechanical: `IExposable` fields that Scribe populates → `= null!` or nullable-with-guard; immutable ctor-set fields → `required`/real `?`. Remediation: file-by-file using the hotspot list as ordering.
- **C-2 [nullable-migration/standard, high]** Replace the 224 `[NotNull]`/`[CanBeNull]` attributes with real NRT (`T` vs `T?`) per `custom-coding-rules.md`; the two systems MUST NOT coexist contradictorily. Remove the `using JetBrains.Annotations;` only from files that no longer reference any JetBrains attribute after migration (some retain `[UsedImplicitly]`). Remediation: pair each attribute removal with the matching nullable annotation in the same edit.

### Correctness / defects (workstream 2)

- **C-3 [defect, high]** `ToolCache.GetStatValue(statDef, workTypeDefs)` caches by `statDef` only (`ItemCache.StatValues`), but the WorkType custom stat value *depends on `workTypeDefs`* (`GetCustomStatValue` → `GetWorkTypesScore(workTypeDefs)`). Within one 24h cache window the first work-type set's score is memoized and returned for every subsequent different set. `EquipmentManagerMapComponent.AssignToolsForWorkTypes` calls `GetThingScore(thing, [workType], …)` once per work type → all but the first work type get a stale WorkType score for the same tool. File: `ToolCache.cs:49-60` + `Ranged/ToolRule.GetThingScore`. Remediation: key the cache entry by `(statDef, workTypeDefs)` for WorkType stats, or do not cache WorkType-dependent stats.
- **C-4 [defect, high]** `EquipmentManagerGameComponent_StatRanges.UpdateStatRange` (`:62-75`): on first insert of a stat it writes `[value,value]` (line 64) but then evaluates the min/max-widening branches against the **stale local `range` (default `FloatRange` = `{0,0}`)** rather than the just-inserted value. For a first observed value `v>0` it ends at `[0,v]` instead of `[v,v]`; for `v<0` at `[v,0]`. This skews `MathHelper.NormalizeValue` for the first sample of every stat → wrong weapon/tool scores until a second wider sample arrives. Remediation: `continue`/return after the insert, or re-read `range` from the dict before the widen checks; add a unit test.
- **C-5 [defect, medium]** `EquipmentManagerMapComponent.UpdateAmmo:338` `ammoDefs.SelectMany(def => map?.listerThings.ThingsOfDef(def))` — if `map` is null `map?.…` yields `null`, and `SelectMany` over a null inner sequence throws `NullReferenceException`. `map` is the component's own map (rarely null mid-tick) but the `?.` signals an expectation it can be; the null branch is unsafe. Remediation: drop the `?.` (map is non-null here) or guard `if (map == null) return;` at method entry; resolve consistently with the C-2 nullable pass.
- **C-6 [defect, medium]** `RangedWeaponCache` accuracy fields (`AccuracyClose/Short/Medium/Long`, and `Dpsa*`) are instance state set conditionally each `Update` (`:303-348`) but **never reset to 0** at the top of `Update`. `Update` runs at most once per 24h window (base `TimedCache` gate), so within a window it is idempotent; but if a weapon's verb/range characteristics change across windows (modded re-defs, CE toggled) a previously-set accuracy band that no longer applies keeps its old value (the `if MinRange<=x && MaxRange>=x` guards only *set*, never *clear*). Low likelihood, real correctness gap. Remediation: zero the accuracy/DPSA fields at `Update` entry.
- **C-7 [defect, low]** `Loadout.GetScore`/`IsAvailable` and `EnsureScoreContext` call `pawn.skills.GetSkill(def)` and `pawn.health.capacities.GetLevel(def)` without guarding `pawn.skills`/`pawn.health` being null. Free-colonist pawns always have these, but newly-spawned/edge pawns in `PawnsFinder.AllMaps_FreeColonistsSpawned` could throw. Remediation: null-guard during the C-2 nullable pass (the NRT flip will surface these as CS8602).
- **C-8 [defect, low]** `PawnCache`/`ToolCache`/`ItemRule`/`WorkTypeRule` cache `_equipmentManager = Current.Game.GetComponent<…>()` in a static field. `FinalizeInit` calls every `ResetCache()` on load, which clears them — so cross-save staleness is handled. But `RangedWeaponRule`/`MeleeWeaponRule`/`ToolRule.ResetCache` clear `_allRelevantThings` and call `ResetEquipmentManagerCache` (shared `ItemRule._equipmentManager`); confirm no caching type is missing from the `FinalizeInit` reset list (e.g. `MeleeWeaponCache`/`RangedWeaponCache` hold no static EM ref — OK). Finding: the per-Thing/per-ThingDef weapon caches on the game component (`_rangedWeaponsCache`, `_rangedWeaponDefsCache`, melee/tool equivalents) are **never cleared on load** and persist `Thing` keys; on load these are fresh (not serialized) so OK, but they grow unbounded over a session and key on `Thing` instances that may be destroyed. Remediation: confirm/limit growth; consider eviction (see C-12).

### Simplification (workstream 3)

- **C-9 [simplification, medium]** `WorkTypeRule.Initialize` (`:224-269`) has **four redundant nested guard clauses**: the inner `if (!_defaultStatWeights.Any(sw => sw.StatDefName == …))` at lines 230, 241-242, 252, 262 re-tests the identical condition already in the enclosing `if` (lines 229, 239, 249, 259). The inner blocks are dead duplicate guards (copy-paste). Remediation: delete the inner `if`s, keep the single outer guard. Reduces ~16 lines and several of the file's nullable warnings.
- **C-10 [simplification, medium]** The five assignment methods in `EquipmentManagerMapComponent` (`AssignAllTools`, `AssignBestTool`, `AssignPrimaryMeleeWeapon`, `AssignPrimaryRangedWeapon`, `AssignToolsForWorkTypes`) plus the two sidearm loops (`UpdateRangedSidearms`/`UpdateMeleeSidearms`) repeat the same boilerplate: build availableWeapons, remove assigned-by-others, add carried weapons, brawler ranged-removal, `CanEquip` + area-restriction filter, score-order, take/queue job, inform sidearm memory. This is the largest copy-paste surface in the codebase. Remediation (needs **Complication Approval** — introduces a shared helper): extract a candidate-filtering helper and a "commit assignment / queue job / update sidearm memory" helper. Note the area-restriction predicate is duplicated verbatim 6+ times — a private static `Predicate<Thing>` factory would be the minimal extraction.
- **C-11 [simplification, low]** Default-stat-weight definitions are split across `ItemRule.DefaultStatWeights` + each rule's `new static DefaultStatWeights` (`RangedWeaponRule:159`, `ToolRule:80`) using `new[]{…}.Union(base)`. Readable but the `new`-shadowing of a base static is a mild smell. Low priority; leave unless the nullable pass touches them.

### Performance (workstream 4)

- **C-12 [performance, medium]** Per-tick (every 60 ticks, 6h debounce) the assignment pipeline rebuilds `assignedByOthers` HashSets via `_pawnCache.Values.SelectMany(pc => pc.AssignedWeapons.Keys)` **once per pawn per pass** (`AssignAllTools`, `AssignBestTool`, primary melee/ranged, sidearm passes). That is O(pawns² × weapons) allocation each cycle. Remediation: compute the assigned-set once per pass and mutate incrementally (the sidearm passes already do `assignedByOthers.Add(...)` after computing it per-pawn — extend that pattern to the others). 
- **C-13 [performance, medium]** `ToolCache.Update` (`:91-97`) iterates **all** `WorkTypeDefsInPriorityOrder` and, for each, does `EquipmentManager.GetWorkTypeRules().FirstOrDefault(rule => rule.WorkTypeDefName == workTypeDef.defName)` — an O(workTypes × rules) linear scan rebuilt per tool cache update. Remediation: build a `Dictionary<string, WorkTypeRule>` once (e.g. on the game component, invalidated on rule edit) and look up by defName.
- **C-14 [performance, low]** `WorkTypeRule.GetGloballyAvailableItems` / `AllRelevantThings` and `ToolRule.AllRelevantThings` recompute via `DefDatabase.AllDefs.Where(...)` LINQ chains; they are cached in static `_allRelevantThings` (good) but the per-call `GetGloballyAvailableItems` (`WorkTypeRule:161-169`) re-allocates a `List` + `SortByDescending` every call with no memoization. Hot only in UI; low priority.
- **C-15 [performance, low]** `GetRangedWeaponDefCache`/`GetMeleeWeaponDefCache` create throwaway `Thing`s via `ThingMaker.MakeThing` (`_RangedWeaponRules.cs:113`) that are cached but never destroyed; `InitializeStatRanges` (`_StatRanges.cs:24-46`) makes a `Thing` per weapon def at init and discards them (GC, but a transient spike). Acceptable; note for awareness.

### Upstream reuse / consolidation (workstream 8 — reuse audit, Architect)

Additional reuse/deduplication pass against the **source** of `LordKuper.Common` (`..\..\rimworld-common\Source\LordKuper.Common`, treated as untrusted first-party data). The upstream-contract pass (C-23…C-25) confirmed EM consumes Common correctly *where it consumes it*; this pass asks the inverse question — **where does EM reimplement what Common already provides?** Findings numbered `RU-N`. The headline: EM contains several near-verbatim reimplementations of types Common has since grown, in violation of the "not a reimplementation of shared utilities" anti-pillar (concept.html) and `custom-common-rules.md` ("do not fork or reimplement what it already provides"). Crucially, **some Common equivalents already contain fixes for EM defects flagged above**, so migrating auto-resolves them.

Common public-surface map built for this pass (namespace `LordKuper.Common[.*]`): `Logger`; `RimWorldTime`; `DefProvider`/`IDefProvider` (testability seam over `DefDatabase<T>`); `Cache.{TimedCache, DefCache<T>, PassionCache}`; `ThingCache`; `StatRanges` (internal); `StatWeight`; `WorkTypeThingRule`; `WorkTypeStatMap`; `SkillStatMap` (internal); `WorkTypeStatMap`; `StatCategory`; `Helpers.{StatHelper, MathHelper, PawnHelper, DefHelper, EnumHelper, TextHelper, PassionHelper, StatDefCategoryComparer}`; `CustomStats.{MeleeWeaponStat(s), RangedWeaponStat(s), ToolStat(s)}`; `Filters.Limits.{StatLimit, PawnSkillLimit, PawnCapacityLimit, PawnTraitLimit}`; `Filters.PawnFilter.*`; `UI.{Labels, Layout, Fields, Sections, Buttons, Checkboxes, Tabs, ScrollView, Windows, Icons, Widgets.*}`; `Compatibility.Vse`.

- **RU-1 [reuse, high] `WorkTypeRule` ⇄ `LordKuper.Common.WorkTypeThingRule` (+ `WorkTypeStatMap`) — divergent-but-mergeable, effort med-high.** `WorkTypeRule.cs` (290 lines) is a near-complete reimplementation of `WorkTypeThingRule` (`LordKuper.Common/WorkTypeThingRule.cs`, public `[PublicAPI]`). Both expose `Label`, `WorkTypeDefName`, `StatWeights`, `DefaultRules`, `SetStatWeight`, `DeleteStatWeight`, `GetGloballyAvailableItems`, `GetThingDefScore`, `GetThingScore`, `ExposeData` and the same private `AllRelevantThings` predicate (`def.IsWeapon && !def.destroyOnDrop && (statBases||equippedStatOffsets)`). EM's `Initialize` (`WorkTypeRule.cs:196-272`) re-derives default stat weights by scanning recipes (`requiredGiverWorkType`, `efficiencyStat`/`workSpeedStat`/`workTable*Stat`), `relevantSkills` via `SkillStatMap`, and the hard-coded `DefaultWorkTypeStats` table (`:18-29`) — **this is exactly `WorkTypeStatMap.Rebuild` (`LordKuper.Common/WorkTypeStatMap.cs:95-185`), including the identical `DefaultWorkTypeStats` literal (Cooking/Hunting/Doctor)**. Behavioral deltas to verify before switching: EM default weight for the hard-coded table is `2f` (`:210`) vs Common `true`-protected at the table's per-stat float (Cooking weights 1–2, Doctor 2 etc. — Common's `DefaultWorkTypeStats` carries explicit weights, EM applies a flat `2f`); EM seeds skill-derived stats at weight `1f` and recipe efficiency at `0.8f`/speed `0.5f` (matches Common). Migration recommendation: **delete `WorkTypeRule`, consume `WorkTypeThingRule`**; if the flat-`2f`-vs-weighted default diverges intentionally (EM wording wins), keep only the default-weight seed and still drop the duplicated recipe/skill/AllRelevantThings/scoring machinery. **Supersedes C-9** (the four redundant double-guards at `WorkTypeRule.cs:230/241-242/252/262` simply vanish — `WorkTypeStatMap.Rebuild` has no such duplication). Risk: `WorkTypeThingRule` serializes `_statWeights` as a `Dictionary<string,StatWeight>` (`LookMode.Value/Deep`) whereas EM serializes a `List<StatWeight>` under the key `"StatWeights"` — **save-compat break**; a load-time migration shim is required (read EM's list form, populate the dict). Classify migration itself as a breaking contract change → approval-gated.

  - **Decision (2026-06-07):** APPROVED for this sprint. Migrate **without** a Scribe save-migration shim — per project `backward_compat=none`, old saves silently lose their persisted WorkType rules (acceptable; users rebuild via defaults). Delete `WorkTypeRule` and consume `Common.WorkTypeThingRule`/`WorkTypeStatMap`. This auto-resolves **C-9** and removes the **largest nullable hotspot (36 distinct NRT sites)**. Sequencing: the non-breaking reuse deletes (RU-3, RU-4, RU-6) and RU-1 land **before** the production nullable flip, so the deleted code is never annotated. (R-C9's shim requirement is waived by the no-shim decision.)

- **RU-2 [reuse, high] `EquipmentManagerGameComponent_StatRanges` (`NormalizeStatValue`/`UpdateStatRange`/`_statRanges`) ⇄ `LordKuper.Common.StatRanges` — exact-duplicate, effort low-med.** `EquipmentManagerGameComponent_StatRanges.cs:49-76` is a line-for-line reimplementation of `LordKuper.Common/StatRanges.cs:42-66` (`NormalizeStatValue` → `UpdateStatRange` → `MathHelper.NormalizeValue(value, range)`), the only difference being EM keys the dict by `stat.defName` (string) and persists it via `IExposable`, while Common keys by `StatDef` and keeps it process-static (not serialized). **Both contain the identical C-4 first-sample-seeding defect** (insert `[v,v]` then evaluate the widen branches against the stale local `range` default `{0,0}` — Common `StatRanges.cs:55-65`, EM `_StatRanges.cs:62-75`). Consequence: migrating to Common does **not** auto-fix C-4 — the bug must be fixed *in Common* (upstream) and consumed, OR EM keeps its own copy and fixes locally. **Blocker:** `Common.StatRanges` is `internal static` — not consumable directly. It is reachable only transitively via `WorkTypeThingRule.GetThingScore`/`GetThingDefScore`. So RU-2 is **gated on RU-1** (and on the weapon/tool rules also moving to Common-style scoring) OR on Common exposing `StatRanges` publicly (a Common-side change, out of EM's edit scope). Recommendation: if EM keeps local scoring, **fix C-4 locally and do not migrate StatRanges**; flag the same defect upstream so Common's copy is fixed too. Cross-ref C-4, R-C2. **Net: this is the one overlap where "consume the library" is blocked by Common's own access modifier — record as an upstream coordination item, not a same-sprint delete.**

  - **Decision (2026-06-07):** UNBLOCKED and APPROVED for migration. The upstream Common fix is **DONE and VERIFIED** (rimworld-common commit `17199b6`: the first-sample-seeding bug is corrected, `StatRanges`/`NormalizeStatValue` made **public**, `Clear()` added, 11 StatRanges tests green; EM builds clean against the rebuilt Common dll dated 2026-06-07). EM will **delete** its duplicate `EquipmentManagerGameComponent_StatRanges` (the `_statRanges` instance dict + `ExposeData_StatRanges`) and the `LegacyCustomStatDefs.NormalizeStatRanges` save-migration, and **consume `Common.StatRanges`** instead. Consequence accepted: stat ranges become **process-global ephemeral** (not save-persisted), rebuilt via `InitializeStatRanges`. This also auto-resolves the EM copy of **C-4**. Note: the C-4 fix now arrives via this Common migration rather than a local EM patch — if RU-2 is sequenced late, ensure no EM scoring runs against the buggy local copy in the interim (or apply the same one-line local fix as a stopgap; plan phase decides). The prior `internal`-access blocker and the "fix upstream first" recommendation above are now resolved.

- **RU-3 [reuse, medium] `ItemCache` ⇄ `LordKuper.Common.ThingCache` — exact-duplicate, effort low.** `ItemCache.cs` (20 lines) re-derives `TimedCache` and adds `protected readonly Dictionary<StatDef,float> StatValues` cleared on `Update`. `LordKuper.Common/ThingCache.cs` (public `[PublicAPI]`) is precisely this: `protected readonly Dictionary<StatDef,float> StatValues`, a timed `Update(RimWorldTime)` that clears on interval. Difference: `ThingCache` holds a `Thing Thing { get; }` (ctor-injected) and uses an internal `RimWorldTime`-diff timer rather than deriving `TimedCache`; EM's `ItemCache` is `Thing`-less and base-`TimedCache`-derived. EM's `RangedWeaponCache`/`MeleeWeaponCache`/`ToolCache` extend `ItemCache`. Migration: either (a) re-base the three weapon caches on `ThingCache` (gains the `Thing` reference they already carry separately) and delete `ItemCache`, or (b) leave as-is — the duplication is 1 dictionary + 1 clear, very low LOC. Recommendation: **low-priority delete**; fold into the C-3 tool-cache fix work since `ToolCache` is touched there anyway. Note RU-3 does not resolve C-3 (the work-type composite-key defect is in `ToolCache.GetStatValue`, EM-specific logic Common does not provide).

- **RU-4 [reuse, medium] `EquipmentManagerStatDefs` ⇄ `StatHelper.GetStatsByCategory` — exact pass-through, effort low.** `EquipmentManagerStatDefs.cs` (35 lines) is five `IReadOnlyList<StatDef>` properties each = `[..StatHelper.GetStatsByCategory(StatCategory.X)]`. Pure thin wrapper around Common with zero added logic. Callers can call `StatHelper.GetStatsByCategory(...)` directly. Migration: **inline the five call-sites and delete the file** (the only nuance: the wrapper materializes once into a list at static init; if callers depend on identity/caching, keep a single cached list — but `StatHelper` already caches per-category in its `Stats` dict, so the wrapper adds nothing). Low risk. Removes 35 lines + 1 file.

- **RU-5 [reuse, low] `WorkTypeRule.DefaultWorkTypeStats` literal ⇄ `WorkTypeStatMap.DefaultWorkTypeStats` — exact-duplicate data, effort low (subsumed by RU-1).** The Cooking/Hunting/Doctor default-stat table is copied verbatim between `WorkTypeRule.cs:18-29` and `WorkTypeStatMap.cs:21-38` (EM stores `IEnumerable<string>` of stat names + applies flat `2f`; Common stores `Dictionary<string,float>` with per-stat weights). Two copies of the same domain knowledge will drift. Resolved automatically by RU-1; listed separately so it is not lost if RU-1 is deferred.

- **RU-6 [reuse, low] `UiHelpers.GetWindowSize` ⇄ `Common.UI.Windows.GetWindowSize` — exact-duplicate, effort low.** `CustomWidgets/UiHelpers.cs:98-103` duplicates `Common.UI.Windows.GetWindowSize(Vector2,Vector2)` (same `Prefs.ScreenWidth/UIScale*0.9f` clamp formula). Broader picture: EM's `UiHelpers` (`DoGapLineHorizontal`, `DoLabeledText`, `DoLabeledRect`, layout-rect math, gap constants) overlaps Common's richer `UI.{Labels, Layout, Sections, Fields, Checkboxes}` namespace (e.g. `Layout.GetTopRowRect/GetRightColumnRect/DoVerticalGap`, `Labels.DoLabel`, `Layout.ElementGap`). Migration: **delete `GetWindowSize` and call `Windows.GetWindowSize`** (trivial); a fuller `UiHelpers`→`Common.UI` migration is a larger, behavior-sensitive UI refactor (pixel-layout parity risk) — defer to a dedicated UI pass, not the alignment sprint. `CycleSettingValue`/`GetSettingCheckboxState`/`ValidNameRegex` are EM-specific (no Common equivalent) — keep.

- **RU-7 [reuse, low] `DoTab_WorkTypes` hand-rolled UI ⇄ `Common.UI.Widgets.WorkTypeThingRuleWidget` — partial-overlap, effort high.** `ManageWeaponRulesDialog_WorkTypes.cs` hand-builds the work-type rule editor tab (rule selector button + stat-weight sliders + available-items icon box) that Common ships as a ready widget `WorkTypeThingRuleWidget.DoWidgetTab(...)` (rule list, `DoRuleStatWeights`, `ThingIconBox`, refresh). Adopting it depends on RU-1 (the widget takes `WorkTypeThingRule`, not EM's `WorkTypeRule`). Recommendation: **bundle with RU-1 if undertaken; otherwise defer** — UI parity risk is high and this is not load-bearing for the alignment sprint. Cross-ref RU-1.

- **RU-8 [reuse, informational] Consistency seam: EM uses raw `DefDatabase<T>` where Common offers `DefProvider.Current`.** EM's `WorkTypeRule`, `ItemRule`, `SkillWeight`, `PawnCapacityWeight`, `PassionLimit`, `_StatRanges` call `DefDatabase<T>.AllDefs`/`.GetNamedSilentFail` directly. Common routes the equivalent through `DefProvider.Current` (the test seam that lets fixtures swap a fake provider — `DefProvider.cs`). This is **not duplication** (it's the base API) but it is why EM's stat/rule logic is hard to unit-test (cross-ref C-18…C-21): migrating the duplicated types (RU-1, RU-4) to Common brings the `DefProvider` testability seam for free. No standalone remediation; a consequence to note in the test-coverage plan.

#### NOT duplicates — keep EM-local (reuse pass, explicit non-findings)

To prevent over-eager consolidation, the following EM types were checked and confirmed to have **no Common equivalent** (or to be legitimate EM-side adaptation per `custom-common-rules.md` "EquipmentManager wording wins"):

- **`SkillWeight`, `PawnCapacityWeight` (weights), `PassionLimit` (passion gate)** — Common provides *limits* (`PawnSkillLimit`, `PawnCapacityLimit`, `StatLimit` — min/max ranges over `DefCache<T>`), which EM **already consumes** in `Loadout` (`Loadout.cs:104,105,110,112`). EM's `SkillWeight`/`PawnCapacityWeight` are single-float *weights* and `PassionLimit` is a `PassionValue` enum gate — different concept, no Common analog. Keep. (These DO carry C-2 nullable + CS8618 cost — see "migration-surface" note below.)
- **`RangedWeaponCache`/`MeleeWeaponCache`/`ToolCache` accuracy & DPS computation** — EM-specific (CE-aware verb/range banding, ammo). Common has no weapon-scoring cache. Keep (subject to C-3/C-6 defect fixes).
- **`CombatExtendedHelper`** — EM-specific optional-dep reflective binding (ADR DM-5). Common has `Compatibility.Vse` (Vanilla Skills Expanded) but nothing for CE. Keep.
- **`LegacyCustomStatDefs`** — EM-side normalization of legacy `EM_`-prefixed stat names onto Common's current `CustomStats` naming. This is adaptation *of* Common, not reimplementation (C-23 already classified it PASS). Keep.
- **`Logger`** — thin EM wrapper that injects `EquipmentManagerMod.ModId` into `Common.Logger.Log*(modId, …)`. This is the *intended* consumption pattern (Common's `Logger` takes a `modId` param precisely so each downstream mod wraps it). Keep — and note it makes C-16 (route 61 raw `Verse.Log.*` calls through the EM `Logger`) the correct fix, NOT "call Common.Logger directly".

## Risks

### Documentation-side risks (BA)
- **stack.html nullable-state drift**: impact=stack.html ships a statement ("production does not yet enable Nullable … scheduled as first sprint") that becomes factually false the moment workstream 1 lands; an unreconciled doc misleads future contributors. mitigation=DM-1 — reconcile stack.html Languages section in the design/design-promote phase, coupled to the nullable-migration completion.
- **Doc/code drift after free-expansion remediation**: impact=free-expansion scope may change behavior (simplification, defect fixes) that invalidates concept.html constraints/pillars or tech-reference notes. mitigation=DM-2 — re-verify concept.html + tech-reference docs against post-remediation code before design-promote.
- **Localization coverage drift if UI changes**: impact=remediation that adds/renames UI elements could introduce new strings without keyed entries, silently regressing localization (workstream 9). mitigation=any new user-facing string must be added to `Resources.Strings` + the Keyed XML in the same change; reviewer (Documentation/UI) verifies.

### Code-side risks (Architect)

- **R-C1 [nullable scope creep]**: impact=131 NRT sites + 224 attribute edits across 36 files is broad; mechanical fixes risk introducing real null-deref masking via `= null!` where a genuine guard is needed (esp. `IExposable` fields and the CE reflection delegates that legitimately may be null). mitigation=migrate per-hotspot-file, prefer real `?` + guard over `null!` for anything dereferenced on the hot path; lean on C-18…C-21 tests to catch regressions; keep `TreatWarningsAsErrors` on throughout.
- **R-C2 [behavioral change from defect fixes]**: impact=fixing C-3 (tool stat cache) and C-4 (stat-range seeding) changes scoring outputs → assignment decisions shift; players may notice different weapon/tool picks. mitigation=add characterization tests around `NormalizeStatValue`/tool scoring before the fix; note the change in PR; this is correct behavior, not a regression.
- **R-C3 [reflection fragility, CE]**: impact=C-25's string-based `AccessTools` bindings break silently if CE renames types/fields; nullable migration must not convert the "may be null on CE-absent" delegates to non-nullable. mitigation=keep CE delegate fields nullable (`?`) with the existing null-guards; do not add `[NotNull]`→non-null to them.
- **R-C4 [static-state test isolation drift]**: impact=`StateIsolationTestBase` snapshots `_equipmentManager` on 5 hard-coded types; adding new tests touching other static caches (`_allRelevantThings`, `_statRanges`) without extending the base re-introduces cross-test bleed. mitigation=extend the base's `CachingTypes`/fields when new static-touching tests are added; the base already throws if a field name goes missing.
- **R-C5 [simplification approval gate]**: impact=C-10 (shared assignment helper) introduces a new abstraction → requires **Complication Approval** before implementing; doing it ad hoc violates the Simplicity Default. mitigation=raise Complication Approval in plan/impl; the minimal version (extract the duplicated area-restriction predicate only) may not need a new layer.
- **R-C6 [unbounded session cache growth]**: impact=per-Thing weapon caches (C-8) key on `Thing` instances and never evict; a long session with many transient weapons grows memory. mitigation=low priority; consider periodic prune keyed on `Thing.Destroyed` if measured to matter — defer unless evidence.
- **R-C7 [free-expansion remediation invalidates docs]** (couples to BA DM-1/DM-2): impact=C-1 lands → stack.html nullable statement false; C-16 logging change is behavior-neutral but touches many files. mitigation=design-promote reconciles stack.html + tech-reference (`csharp-net48.md` nullable note) after remediation.
- **R-C8 [jb-inspect unavailable]**: impact=the ReSharper inspection step of the mandated lint flow cannot run on `.slnx` here (MSB4236); some style/inspection findings may go unmeasured. mitigation=rely on NetAnalyzers (clean baseline) + `dotnet format --verify-no-changes`; if jb-inspect is required for sign-off, run it against the `.csproj` files individually or repair the BuildTools workload locator out of band.
- **R-C9 [reuse migration = breaking save-format change]**: impact=RU-1 (`WorkTypeRule`→`WorkTypeThingRule`) changes the serialized shape of work-type rules from a `List<StatWeight>` under key `"StatWeights"` to `WorkTypeThingRule`'s `Dictionary<string,StatWeight>` — existing saves would silently lose their customized work-type weights without a load-time shim. Also subtle scoring drift if EM's flat `2f` default differs from Common's per-stat weighted defaults. mitigation=treat RU-1 as an approval-gated breaking contract change (backward_compat policy applies); require a Scribe load-migration that reads the legacy list form and populates the dict; add characterization tests on work-type scores (cross-ref C-19, R-C2) before/after. If the migration shim is not in scope this sprint, **defer RU-1** and take only the non-breaking reuse wins (RU-3 ItemCache, RU-4 EquipmentManagerStatDefs, RU-6 GetWindowSize). RU-2 additionally blocked: `Common.StatRanges` is `internal` — coordinate an upstream change (expose it / fix C-4 upstream) before EM can consume it.

- **Hardcoded strings that exist are developer/debug log lines, NOT user-facing.** `Log.Error` / `Log.Warning` / `Log.Message` calls (e.g. in `CombatExtendedHelper.cs`, `RangedWeaponCache.cs`, `MeleeWeaponCache.cs`, `ToolCache.cs`, `EquipmentManagerMod.cs`, `EquipmentManagerMapComponent.cs`) carry hardcoded English text prefixed "Equipment Manager: …".
