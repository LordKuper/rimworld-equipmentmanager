EquipmentManager — Remediation PRD

3 goals · 9 stories · 41 AC · 6 non-goals · updated 2026-06-07

Problem

This is not a feature sprint. The full audit (audit.md) catalogued 25 code findings (C-1…C-25), 8 reuse/consolidation findings (RU-1…RU-8), and 6 documentation items (DM-1…DM-6) against the EquipmentManager codebase and design corpus. This PRD converts every confirmed remediation item into objectively verifiable acceptance criteria so the implementation-review phase has concrete, traceable targets. The "user" here is the mod maintainer; the value delivered is a codebase that is defect-free, simplified, standards-conformant, performant, consolidated onto LordKuper.Common (no reimplementation of shared utilities), and fully nullable-aware — without changing any player-facing behavior beyond the correctness fixes the audit identified.

Goals

  1. G1

    Land the headline production nullable migration: Nullable enable on the production csproj, build green under TreatWarningsAsErrors, all NRT sites resolved, and JetBrains nullability attributes replaced with real nullable reference types.

  2. G2

    Remediate every audit-confirmed defect, simplification, performance, standard-conformance, and reuse/consolidation finding — or record it explicitly as deferred with rationale — while keeping upstream consumption contract-correct (no forking).

  3. G3

    Reconcile design docs and tests with the post-remediation code: extend unit coverage for the audited pure-logic units, and close identified doc-drift so the corpus matches reality.

User stories

The single role for this remediation sprint is the mod maintainer (LordKuper / future contributors). Stories are grouped by workstream; each maps to an acceptance-criteria block below.

Mod maintainer 9
  • as a maintainer, I want the production project to compile under Nullable enable with zero warnings and no leftover JetBrains nullability attributes, so that nullability intent is enforced by the compiler instead of stale annotations. (US1 → AC group: Nullable migration)
  • as a maintainer, I want the stat-range and tool-cache scoring defects fixed, so that weapon/tool assignment decisions are computed correctly rather than from stale or first-sample-skewed values. (US2 → AC group: Correctness / defects)
  • as a maintainer, I want EM's local reimplementations of LordKuper.Common utilities deleted and replaced with the library's public surface, so that the anti-pillar "not a reimplementation of shared utilities" holds and there is one source of truth. (US3 → AC group: Reuse / consolidation)
  • as a maintainer, I want dead duplicate guard clauses removed, so that the codebase carries no accidental complexity. (US4 → AC group: Simplification)
  • as a maintainer, I want the hot-path assignment pipeline's redundant per-pawn allocations and linear scans eliminated, so that the tick cost scales acceptably with colony size. (US5 → AC group: Performance)
  • as a maintainer, I want all diagnostics routed through the project Logger wrapper and the solution consistently formatted, so that the code conforms to custom-coding-rules.md. (US6 → AC group: Standard conformance)
  • as a maintainer, I want genuine unit tests around the audited pure-logic units, so that the defect fixes are characterized and regressions are caught. (US7 → AC group: Test coverage)
  • as a maintainer, I want verification that LordKuper.Common and SimpleSidearms are still consumed contract-correctly with no forking, so that the upstream integration stays intact through the consolidation. (US8 → AC group: Upstream contract)
  • as a maintainer, I want the design docs reconciled with the post-remediation code and localization verified clean, so that the corpus does not mislead future contributors. (US9 → AC groups: Localization, Doc reconciliation)

Sequencing constraint

One ordering constraint is load-bearing across the AC groups and is itself an acceptance criterion (AC-1): the non-breaking reuse deletes (RU-3 ItemCache, RU-4 EquipmentManagerStatDefs, RU-6 GetWindowSize) and the approved RU-1 (WorkTypeRule → Common.WorkTypeThingRule) and RU-2 (StatRanges) migrations MUST land before the production nullable flip (AC group: Nullable migration). Deleting these files first removes the single largest nullable hotspot (WorkTypeRule.cs, 36 distinct NRT sites) and the wrapper files, so the nullable migration is performed only on code that survives. Annotating code that is about to be deleted is wasted and forbidden by AC-1.
