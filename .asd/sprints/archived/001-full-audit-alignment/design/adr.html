ADR-0001 · Enable nullable reference types on the production project

Context

The production project Source/EquipmentManager/EquipmentManager.csproj targets net48 with LangVersion latest, WarningLevel 9999 and TreatWarningsAsErrors, but does not set a nullable context. Nullability intent is instead carried by 224 JetBrains nullability attributes (205 [NotNull] + 19 [CanBeNull]) across 36 files, each file also carrying using JetBrains.Annotations;. The test project (EquipmentManager.Tests.csproj) already builds under Nullable enable, and the upstream LordKuper.Common library is already fully nullable. Nullable enable on the production project is the stated target standard (custom-coding-rules.md) and the headline deliverable of this sprint (AC-9…AC-14, finding C-1/C-2).

Flipping -p:Nullable=enable on a clean rebuild of the current code surfaces a measured 131 distinct sites / 300 occurrences across 32 files. The dominant code is CS8618 (×132, uninitialized non-nullable field/property) — overwhelmingly IExposable save/load fields that Scribe populates by reflection during deserialization (no constructor runs), plus the static reflection-delegate fields in CombatExtendedHelper.cs and the weapon caches that are bound once via Harmony AccessTools and are legitimately null when Combat Extended is absent. Two nullability systems (JetBrains attributes + real NRT) must not coexist contradictorily.

Constraint: under TreatWarningsAsErrors the build must reach zero NRT diagnostics, so every site needs a real resolution rather than a tolerated warning. Forces in play: (a) mechanical breadth (32 files) versus the risk of masking genuine null-derefs with blanket = null!; (b) the RimWorld lifecycle reality that Scribe/reflection populate fields outside any constructor, which the compiler cannot see; (c) the soft-dependency reflection fields that are genuinely nullable.

Decision

Set <Nullable>enable</Nullable> on the production csproj and resolve every surfaced NRT site with a real annotation or guard. No blanket #nullable disable, no #pragma warning disable to mask CS86xx/CS9264, and no mass ! suppression. Remove all 224 JetBrains nullability attributes (replacing each with the matching T vs T? in the same edit) and drop using JetBrains.Annotations; from every file that no longer references a JetBrains attribute — retaining the using only where [UsedImplicitly] (×13, not a nullability attribute) still appears.

Resolution patterns, in priority order:

  • Genuinely-nullable references (dereferenced on any path, especially the hot path) → declare T? with a real null-guard. This is the default; prefer it over suppression.
  • CE reflection-delegate / soft-dependency fields (CombatExtendedHelper.cs and the two weapon caches) → declare T? and keep the existing CE-absent null-guards. These are never converted to non-null and never assigned = null! (R-C3, AC-14).
  • IExposable fields populated by Scribe / reflection (the CS8618 majority) → the established RimWorld-lifecycle pattern: a non-nullable field initialized = null! where the value is always present after ExposeData/FinalizeInit and the field is contractually non-null at every read. This mirrors how LordKuper.Common already annotates its own IExposable types (e.g. WorkTypeThingRule._statWeights = new() for collections; reference fields it cannot construct use the same lifecycle convention). Collection fields prefer real initializers (= new()) over = null!; = null! is reserved for reference fields that genuinely have no construction-time value and are guaranteed populated by the load/init lifecycle.
  • Immutable fields set once at construction → real non-null types via constructor assignment or required where applicable (e.g. the CS9264 auto-prop at ManageWeaponRulesDialog.cs:30).
  • Variance mismatches (CS8619 IEnumerable<StatDef?> vs IEnumerable<StatDef>) → fix at the source of the sequence (filter nulls or correct the element type) rather than casting.

Migrate file-by-file using the audit hotspot ordering. Keep TreatWarningsAsErrors on throughout so no site is silently deferred. This decision is sequenced after ADR-0002's reuse deletes (AC-1): the largest hotspot, WorkTypeRule.cs (36 distinct sites), and the wrapper files are deleted by ADR-0002 before this flip, so they are never annotated.

Consequences

Positive

  • Nullability intent is enforced by the compiler, not by stale attributes that no tool checks at build time.
  • One nullability system across production, tests, and the upstream library — no contradictory dual annotations.
  • The flip surfaces real latent null-deref risks (C-5 UpdateAmmo map, C-7 pawn.skills/pawn.health) as CS8602/CS8604, which are then fixed as part of the same pass rather than lying dormant.
  • 224 attributes + 36 redundant usings removed → less ceremony per file.

Negative

  • Broad, mechanical edit across 32 files; risk of masking a genuine null-deref by reaching for = null! where a guard was needed (mitigated by the priority order above + the new characterization tests, ADR-0004 / AC-25…AC-29).
  • = null! on IExposable fields is a compiler-trust assertion the runtime does not verify; if the load lifecycle ever fails to populate one, the NRE moves from a clear annotation to a runtime surprise. Accepted because Scribe always populates these and the alternative (nullable + guard on every read) adds noise to dozens of hot-path reads.
  • The stack.html statement that the production project is "not yet nullable, scheduled as first sprint" becomes false the moment this lands and must be reconciled in design-promote (DM-1 / AC-36).

Alternatives considered

  • Per-file #nullable enable opt-in (incremental) — rejected: leaves the project in a mixed state indefinitely, contradicts the single-target-standard goal, and the measured cost is bounded enough to do in one sprint.
  • Keep JetBrains attributes alongside real NRT — rejected: two systems that can disagree; custom-coding-rules.md mandates real NRT and the attributes are unchecked at build time.
  • Blanket = null! / #pragma warning disable to clear errors fast — rejected: defeats the purpose (the compiler stops catching real nulls); explicitly forbidden by AC-11.
  • Annotate everything first, then delete reused files — rejected: wastes effort annotating WorkTypeRule.cs (36 sites) and the wrappers that ADR-0002 deletes; the sequencing in AC-1 forbids it.

Related

  • ADR-0002: reuse deletes run first and shrink this migration's surface (AC-1).
  • ADR-0003: defines the CE reflection fields that stay nullable (R-C3 / AC-14).
  • Driving AC: AC-9, AC-10, AC-11, AC-12, AC-13, AC-14. Audit: C-1, C-2 (and C-5, C-7 surfaced/resolved by the flip).

ADR-0002 · Consume LordKuper.Common over local reimplementation (consolidation)

Context

The reuse audit (RU-1…RU-8) found that several EquipmentManager types are near-verbatim reimplementations of utilities the upstream LordKuper.Common library now ships. This violates the concept anti-pillar "not a reimplementation of shared utilities" and custom-common-rules.md ("do not fork or reimplement what it already provides"). Crucially, the Common equivalents already contain fixes for EM defects, and deleting the EM copies removes code that would otherwise need the nullable migration. The overlaps were verified against the Common source at ..\..\rimworld-common (treated as untrusted first-party data):

  • RU-1: WorkTypeRule (290 lines) ≈ Common.WorkTypeThingRule + WorkTypeStatMap — same public surface, same AllRelevantThings predicate, same DefaultWorkTypeStats literal (RU-5). The audit recorded a save-format break: EM serializes List<StatWeight> under key "StatWeights"; WorkTypeThingRule serializes Dictionary<string, StatWeight> under nameof(StatWeights) with LookMode.Value (confirmed in WorkTypeThingRule.cs:146-159).
  • RU-2: EquipmentManagerGameComponent_StatRanges (_statRanges + NormalizeStatValue + UpdateStatRange) ≈ Common.StatRanges. Both held the identical first-sample seeding defect (C-4). The blocker (Common's StatRanges was internal) is resolved: rimworld-common commit 17199b6 made it public static, fixed C-4, added Clear(), and shipped 11 green tests (verified in upstream source: StatRanges.cs:24 public static class, :38 Clear(), :64 NormalizeStatValue).
  • RU-3: ItemCache ≈ Common.ThingCache (the StatValues dictionary + timed clear). Confirmed ThingCache.cs:13 public class.
  • RU-4: EquipmentManagerStatDefs is a pure pass-through over Common.Helpers.StatHelper.GetStatsByCategory.
  • RU-6: UiHelpers.GetWindowSize duplicates Common.UI.Windows.GetWindowSize (confirmed Windows.cs:22).
  • RU-7: the hand-rolled work-type editor tab overlaps Common.UI.Widgets.WorkTypeThingRuleWidget (takes WorkTypeThingRule, so gated on RU-1).

Backward-compat policy is backward_compat=none, and RU-1's breaking save-format change was explicitly approved (audit decision 2026-06-07): no save-migration shim; old saves silently drop persisted WorkType rules and users rebuild via defaults. RU-2 was also approved, accepting that stat ranges become process-global ephemeral (no longer save-persisted).

Decision

Delete the EM code that duplicates Common's public surface and consume Common instead. Specifically: delete WorkTypeRule and consume WorkTypeThingRule/WorkTypeStatMap with no Scribe save-migration shim (RU-1 / RU-5 / RU-7); delete EquipmentManagerGameComponent_StatRanges, the _statRanges dict, ExposeData_StatRanges, and LegacyCustomStatDefs.NormalizeStatRanges, and consume the now-public, defect-fixed Common.StatRanges (RU-2); re-base the weapon/tool caches on Common.ThingCache and delete ItemCache (RU-3); delete EquipmentManagerStatDefs and inline StatHelper.GetStatsByCategory(StatCategory.X) at its five call-sites (RU-4); delete UiHelpers.GetWindowSize and call Common.UI.Windows.GetWindowSize (RU-6); adopt WorkTypeThingRuleWidget bundled with RU-1, or defer it with rationale (RU-7).

Sequencing (load-bearing, AC-1): all of the above land and build green before the ADR-0001 nullable flip, so deleted code is never annotated. WorkTypeRule.cs alone removes the 36-site nullable hotspot.

Auto-resolutions: RU-1 deletes the four redundant double-guards (C-9) and the duplicated DefaultWorkTypeStats literal (RU-5); RU-2 brings the upstream C-4 fix. The DefProvider testability seam (RU-8) comes along for free once the duplicated types move to Common, easing the test workstream (C-18…C-21).

Kept local — explicitly NOT migrated (verified to have no Common equivalent or to be legitimate EM-side adaptation; AC-33):

TypeWhy kept
SkillWeight, PawnCapacityWeightSingle-float weights; Common offers limits (min/max ranges) which EM already consumes in Loadout. Different concept, no Common analog.
PassionLimitA PassionValue enum gate; no Common equivalent.
RangedWeaponCache / MeleeWeaponCache / ToolCache scoringEM-specific CE-aware verb/range banding + ammo + work-type stat logic; Common has no weapon-scoring cache. (Caches re-base on ThingCache per RU-3 but the scoring stays EM-local.)
CombatExtendedHelperEM-specific optional-dep reflective binding (see ADR-0003). Common has no CE compatibility layer.
LegacyCustomStatDefs (remainder, after NormalizeStatRanges is removed)EM-side normalization of legacy EM_ stat names onto Common's current CustomStats naming — adaptation of Common, not reimplementation (C-23 PASS).
Logger wrapperThin wrapper injecting EquipmentManagerMod.ModId into Common.Logger — the intended consumption pattern (Common's Logger takes a modId param so each downstream mod wraps it). Keep; it makes C-16 the correct fix.
UiHelpers remainder (CycleSettingValue, GetSettingCheckboxState, ValidNameRegex, gap/label helpers)EM-specific; only GetWindowSize is a duplicate. A fuller UiHelpers→Common.UI migration is a separate behavior-sensitive UI pass, out of scope.

Consequences

Positive

  • Restores the "not a reimplementation of shared utilities" anti-pillar; one source of truth for work-type rules, stat ranges, the thing cache, stat-category lookups, and window sizing.
  • Shrinks the nullable-migration surface before the flip (≈36 distinct sites from WorkTypeRule alone, plus the wrapper files).
  • Inherits the upstream C-4 fix (RU-2) and erases C-9 / RU-5 by deletion rather than by patching.
  • Brings the DefProvider test seam into EM's stat/rule paths, unblocking the test workstream.

Negative

  • Breaking save-format change (RU-1): existing saves silently lose customized work-type rules; no migration shim. Accepted under backward_compat=none; users rebuild from defaults.
  • Stat ranges become process-global ephemeral (RU-2): no longer save-persisted; rebuilt each process via InitializeStatRanges. A first-tick scoring pass may run against a not-yet-fully-seeded range until samples accumulate — behaviorally equivalent to a fresh load, accepted.
  • Possible scoring drift if EM's flat 2f default work-type stat weight differs from Common's per-stat weighted DefaultWorkTypeStats; this changes assignment decisions. Characterized by tests before/after (ADR-0004, AC-26).
  • Tighter coupling to the Common version: RU-2 requires the Common build at or past commit 17199b6. EM already builds against the rebuilt 1.6 dll (2026-06-07).
  • RU-7 (widget adoption) carries UI pixel-parity risk; may be deferred (AC-7).

Alternatives considered

  • Add a Scribe load-migration shim for RU-1 (read the legacy list form, populate the dict) — rejected: backward_compat=none makes it unnecessary churn; the approved decision is to drop old persisted rules.
  • Keep EM's StatRanges copy and fix C-4 locally — rejected: the upstream fix already shipped and was verified; keeping a local copy re-introduces the very duplication this ADR removes and risks the two copies drifting again.
  • Defer RU-1 and take only the non-breaking wins (RU-3/RU-4/RU-6) — rejected: RU-1 was approved, and deferring it leaves the largest nullable hotspot in place and the anti-pillar partly violated.
  • Migrate UiHelpers wholesale to Common.UI — rejected for this sprint: behavior-sensitive layout refactor with pixel-parity risk; only the exact GetWindowSize duplicate is removed.
  • Delete the kept-local weight/limit/passion types in favor of Common limits — rejected: they are a different concept (weights/enum gate vs min-max limits); not duplicates (AC-33).

Related

  • ADR-0001: this ADR's deletes run first and shrink the nullable surface (AC-1).
  • ADR-0003: confirms Common stays a compile-only, non-forked reference through the consolidation.
  • ADR-0004: the scoring-drift risk (RU-1/RU-2) is gated by the characterization-test policy.
  • Driving AC: AC-1…AC-8 (plus AC-16 C-4 via RU-2, AC-17 C-9 via RU-1, AC-33 kept-local). Audit: RU-1…RU-8, C-4, C-9, R-C9.

ADR-0003 · Dependency-integration pattern (hard typed refs vs reflective soft-dep binding)

Provenance: reverse-engineered from existing code (Source/EquipmentManager/CombatExtendedHelper.cs, EquipmentManager.csproj, About/About.xml, the weapon caches). Source: the as-built integration in the EquipmentManager codebase.

Context

EquipmentManager integrates with four external pieces of code with different coupling needs, and the codebase already implements a consistent (but undocumented) pattern for each. The decisions-log flagged a candidate ADR for this; this ADR reverse-engineers the as-built contract so future contributors do not break it. The dependencies:

  • Lib.Harmony 2.4.2 — patching framework. One patch (DefGeneratorPatch postfix inserting the EM_Loadout pawn column) plus AccessTools used as the reflection toolkit for the CE binding.
  • LordKuper.Common 1.6 — hard upstream library, but version-scoped: a runtime modDependency only on game v1.6 (About.xml modDependenciesByVersion); older game versions of the mod do not depend on it.
  • SimpleSidearms 1.6 — hard modDependency across versions; consumed via concrete types (CompSidearmMemory, StatCalculator, WeaponAssingment, Enums, SidearmsDefOf).
  • Combat Extended — soft, optional integration: loadAfter only, no modDependency, and the mod must run correctly whether or not CE is present.

The forces: hard deps want compile-time type safety and IDE support; the soft dep cannot have a compile reference (CE may be absent at runtime) yet must be used when present; and none of these may be forked or vendored (upstream-contract invariant, C-23…C-25 all PASS).

Decision

Record the as-built pattern as the standing integration contract: hard dependencies are consumed through direct, compile-only typed references; the soft (optional) dependency is bound entirely by reflection with graceful degradation. No dependency is forked or vendored into the repo.

  • Hard deps (Common, SimpleSidearms, Harmony): referenced by HintPath with <Private>False</Private> — compile against the assembly, but do not copy it to the build output (the host mod supplies it at runtime). Harmony additionally uses ExcludeAssets=runtime + PrivateAssets=all (compile-only NuGet). Common's hard-dependency status is version-scoped in About.xml (runtime modDependency for v1.6 only); SimpleSidearms is a hard modDependency. Reference resolution is path-overridable (LORDKUPER_COMMON_DIR, RIMWORLD_DIR, SIMPLE_SIDEARMS_DIR) with sensible defaults in Directory.Build.props.
  • Soft dep (Combat Extended): no compile reference. Bound at runtime via Harmony AccessTools.TypeByName / FieldRefAccess / MethodDelegate in CombatExtendedHelper and the two weapon caches' Initialize methods. The reflective handles are resolved once; every lookup logs on failure and the caches degrade gracefully (all CE-derived values fall back to a no-CE path). About.xml declares CE in loadAfter only.
  • Upstream names consumed verbatim: SimpleSidearms' own misspelled type WeaponAssingment is the real upstream type name and is consumed as-is — it must NOT be "corrected" (C-24, AC-31).
  • Nullability coupling (links ADR-0001): the CE reflective handles are legitimately null when CE is absent, so under Nullable enable they stay T? with their existing guards and are never forced non-null (R-C3, AC-14).

This ADR documents an existing pattern and prescribes no code change beyond keeping it intact; it is the architectural rationale future contributors must respect when adding or modifying an integration.

Consequences

Positive

  • Hard deps get full compile-time type safety and refactoring support; soft dep imposes zero hard runtime requirement, so the mod loads with or without CE.
  • Private=False avoids shipping duplicate assemblies and the load conflicts that would cause.
  • Clear, repeatable rule for the next integration: hard → typed ref; optional → reflection + degrade.
  • No forking; upstream contracts stay intact and updatable.

Negative

  • The CE binding is string-based and fragile: a CE rename of a type/field/method breaks it silently at the lookup. Mitigated by per-lookup failure logging and graceful degradation, but not by the compiler (R-C3).
  • Build requires the sibling Common checkout / the resolved reference paths to be present; a missing path fails the build fast (acceptable, documented in the tech-reference).
  • Version-scoped Common dependency means the contract is a 1.6-only expectation; the integration shape differs across supported game versions.

Alternatives considered

  • Add a compile-time reference to Combat Extended — rejected: would make CE a hard requirement (the mod would fail to load without it) and there is no stable distributable CE reference assembly; reflection is the only way to keep CE optional.
  • Vendor / fork Common or SimpleSidearms into the repo — rejected: violates the upstream-contract invariant and causes duplicate-assembly load conflicts; Private=False compile-only is the correct mechanism.
  • "Fix" the WeaponAssingment spelling — rejected: it is SimpleSidearms' own public type name; renaming would not compile against the real assembly.
  • Make Common a hard dependency on all game versions — rejected: contradicts the existing version-scoped About.xml contract; older versions never depended on Common.

Related

  • ADR-0001: CE reflective fields stay nullable under the migration (AC-14).
  • ADR-0002: consolidation keeps Common a compile-only, non-forked reference (AC-30).
  • Driving AC: AC-30, AC-31, AC-32, AC-33. Audit: DM-5, C-23, C-24, C-25.
  • This ADR is promoted to design/architecture/adr/ in design-promote (satisfies AC-40).

ADR-0004 · Defect & performance remediation policy

Context

Most audit defects are mechanical fixes that belong in the plan, not in an ADR. Two carry a genuine cross-cutting decision and are recorded here so the implementation phase does not treat them as ordinary patches:

  • C-3 — tool-stat cache key contract. ToolCache.GetStatValue(statDef, workTypeDefs) caches by statDef only, but the WorkType custom-stat value depends on workTypeDefs (via GetWorkTypesScore). Within one 24h cache window the first work-type set's score is memoized and returned for every subsequent different set, so AssignToolsForWorkTypes (one call per work type) gives all-but-the-first work type a stale score. The StatValues cache contract cannot represent a work-type-dependent value — fixing it changes the cache key contract, not just a line of code.
  • Behavioral change from defect fixes (R-C2). Fixing C-3 and C-4 (the latter via ADR-0002's RU-2 migration) changes scoring outputs, which changes weapon/tool assignment decisions players observe. This is correct behavior, not a regression, but it must not land silently.

The mechanical performance/defect items (C-12 incremental assignedByOthers set, C-13 defName-keyed rule lookup dictionary, C-5/C-6/C-7/C-8) carry no architectural decision and are left to the plan; C-5/C-7 are resolved by the ADR-0001 flip surfacing them as CS86xx.

Decision

Two cross-cutting rules for the remediation:

  1. Cache-key correctness over caching: for work-type-dependent tool stats, either key the cache entry by the composite (statDef, workTypeDefs) or do not cache the WorkType-dependent stat at all. Caching a value whose inputs are not all in the key is forbidden — correctness wins over the cache hit (C-3, AC-15). Note the composite key is a local EM concern: Common.ThingCache (adopted in RU-3) does not provide work-type-aware keying, so this fix lives in EM's ToolCache logic on top of the re-based cache.
  2. Characterize before changing behavior: any fix that shifts scoring/assignment output (C-3, and C-4 via the RU-2 migration) must be accompanied by a characterization test on the affected math before the fix lands, and the behavioral change is called out in the PR. The first-sample [v,v] assertion (C-4) and the differing-work-type-set assertion (C-3) are required tests (AC-25, AC-29).

The mechanical performance fixes (C-12, C-13) are mandated by their own AC (AC-19, AC-20) and need no decision here beyond "do them"; they are referenced for completeness, not re-decided.

Consequences

Positive

  • Tool scores become per-work-type correct; the silent stale-score class of bug is closed at the cache-contract level, not patched per call-site.
  • Behavioral shifts are captured by tests and disclosed, so reviewers and the maintainer can distinguish "intended correctness change" from "regression".
  • Keeps the ADR corpus lean: only the two items with real decision content are recorded; mechanical fixes stay in the plan (Simplicity Default).

Negative

  • A composite cache key (or no-cache carve-out) for WorkType stats slightly raises tool-cache cost or key complexity versus the (incorrect) single-key cache. Accepted: correctness is non-negotiable and the work-type set is small.
  • Requiring a characterization test before each behavioral fix adds up-front test effort, and the post-fix assignment output will differ from prior saves' expectations (players may notice different picks). Accepted and disclosed.

Alternatives considered

  • Fold C-3 into ADR-0002 (consolidation) or leave it purely plan-level — rejected: C-3 is an EM-local cache-contract decision that survives the RU-3 migration (Common's ThingCache has no work-type keying), so it deserves its own recorded contract rather than being buried in the consolidation or treated as a one-line patch.
  • Manufacture separate ADRs for C-12 / C-13 — rejected: they are mechanical optimizations with no tradeoff to decide (Simplicity Default forbids ADRs with no decision content); they remain plan tasks under AC-19/AC-20.
  • Skip characterization tests and just ship the fixes — rejected: scoring changes are player-visible; without before/after tests a real regression would be indistinguishable from the intended correctness change (R-C2).

Related

  • ADR-0002: C-4 is fixed via the RU-2 migration there; this ADR governs the test discipline around the resulting behavioral change.
  • Driving AC: AC-15 (C-3), AC-16 (C-4 via RU-2), AC-25, AC-29; performance AC-19 (C-12), AC-20 (C-13). Audit: C-3, C-4, C-12, C-13, R-C2.

Open questions (non-blocking)

  • RU-1 default-weight parity (OQ-1). The audit flagged a possible scoring divergence: EM applied a flat 2f default weight for the hard-coded work-type stats, whereas Common.WorkTypeStatMap.DefaultWorkTypeStats carries explicit per-stat weights (Cooking 1–2, Doctor 2, etc.). After deleting WorkTypeRule, EM inherits Common's weighted defaults. Decision deferred to impl + the AC-26 characterization test: confirm whether the resulting assignment behavior is acceptable as-is (preferred, one source of truth) or whether an EM-side default override is warranted ("EquipmentManager wording wins" per custom-common-rules.md). Not blocking — the consolidation proceeds; the test phase decides if an override is needed.
  • RU-7 widget adoption (OQ-2). Whether to adopt Common.UI.Widgets.WorkTypeThingRuleWidget this sprint (bundled with RU-1) or defer it (UI pixel-parity risk). AC-7 allows either; the plan/impl phase decides based on parity risk. Not blocking.
  • C-10 assignment-helper extraction (OQ-3). The shared candidate-filter / commit-job helper is a new abstraction requiring Complication Approval (R-C5, AC-18). It is proposed, not mandated; the minimal form (extract only the duplicated area-restriction Predicate<Thing> factory) may not need a new layer. Deferred to plan/impl with the approval gate. Not an architecture decision for this ADR set.
