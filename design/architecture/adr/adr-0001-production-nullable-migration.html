ADR-0001 · Enable nullable reference types on the production project

accepted · subsystem N/A · updated 2026-06-07
accepted subsystem: N/A ADR-0001

Context

The production project Source/EquipmentManager/EquipmentManager.csproj targets net48 with LangVersion latest, WarningLevel 9999 and TreatWarningsAsErrors, but does not set a nullable context. Nullability intent is instead carried by 224 JetBrains nullability attributes (205 [NotNull] + 19 [CanBeNull]) across 36 files, each file also carrying using JetBrains.Annotations;. The test project (EquipmentManager.Tests.csproj) already builds under Nullable enable, and the upstream LordKuper.Common library is already fully nullable. Nullable enable on the production project is the stated target standard (custom-coding-rules.md) and the headline deliverable of this sprint (AC-9…AC-14, finding C-1/C-2).

Flipping -p:Nullable=enable on a clean rebuild of the current code surfaces a measured 131 distinct sites / 300 occurrences across 32 files. The dominant code is CS8618 (×132, uninitialized non-nullable field/property) — overwhelmingly IExposable save/load fields that Scribe populates by reflection during deserialization (no constructor runs), plus the static reflection-delegate fields in CombatExtendedHelper.cs and the weapon caches that are bound once via Harmony AccessTools and are legitimately null when Combat Extended is absent. Two nullability systems (JetBrains attributes + real NRT) must not coexist contradictorily.

Constraint: under TreatWarningsAsErrors the build must reach zero NRT diagnostics, so every site needs a real resolution rather than a tolerated warning. Forces in play: (a) mechanical breadth (32 files) versus the risk of masking genuine null-derefs with blanket = null!; (b) the RimWorld lifecycle reality that Scribe/reflection populate fields outside any constructor, which the compiler cannot see; (c) the soft-dependency reflection fields that are genuinely nullable.

Decision

Set <Nullable>enable</Nullable> on the production csproj and resolve every surfaced NRT site with a real annotation or guard. No blanket #nullable disable, no #pragma warning disable to mask CS86xx/CS9264, and no mass ! suppression. Remove all 224 JetBrains nullability attributes (replacing each with the matching T vs T? in the same edit) and drop using JetBrains.Annotations; from every file that no longer references a JetBrains attribute — retaining the using only where [UsedImplicitly] (×13, not a nullability attribute) still appears.

Resolution patterns, in priority order:

  • Genuinely-nullable references (dereferenced on any path, especially the hot path) → declare T? with a real null-guard. This is the default; prefer it over suppression.
  • CE reflection-delegate / soft-dependency fields (CombatExtendedHelper.cs and the two weapon caches) → declare T? and keep the existing CE-absent null-guards. These are never converted to non-null and never assigned = null! (R-C3, AC-14).
  • IExposable fields populated by Scribe / reflection (the CS8618 majority) → the established RimWorld-lifecycle pattern: a non-nullable field initialized = null! where the value is always present after ExposeData/FinalizeInit and the field is contractually non-null at every read. This mirrors how LordKuper.Common already annotates its own IExposable types (e.g. WorkTypeThingRule._statWeights = new() for collections; reference fields it cannot construct use the same lifecycle convention). Collection fields prefer real initializers (= new()) over = null!; = null! is reserved for reference fields that genuinely have no construction-time value and are guaranteed populated by the load/init lifecycle.
  • Immutable fields set once at construction → real non-null types via constructor assignment or required where applicable (e.g. the CS9264 auto-prop at ManageWeaponRulesDialog.cs:30).
  • Variance mismatches (CS8619 IEnumerable<StatDef?> vs IEnumerable<StatDef>) → fix at the source of the sequence (filter nulls or correct the element type) rather than casting.

Migrate file-by-file using the audit hotspot ordering. Keep TreatWarningsAsErrors on throughout so no site is silently deferred. This decision is sequenced after ADR-0002's reuse deletes (AC-1): the largest hotspot, WorkTypeRule.cs (36 distinct sites), and the wrapper files are deleted by ADR-0002 before this flip, so they are never annotated.

Consequences

Positive

  • Nullability intent is enforced by the compiler, not by stale attributes that no tool checks at build time.
  • One nullability system across production, tests, and the upstream library — no contradictory dual annotations.
  • The flip surfaces real latent null-deref risks (C-5 UpdateAmmo map, C-7 pawn.skills/pawn.health) as CS8602/CS8604, which are then fixed as part of the same pass rather than lying dormant.
  • 224 attributes + 36 redundant usings removed → less ceremony per file.

Negative

  • Broad, mechanical edit across 32 files; risk of masking a genuine null-deref by reaching for = null! where a guard was needed (mitigated by the priority order above + the new characterization tests, ADR-0004 / AC-25…AC-29).
  • = null! on IExposable fields is a compiler-trust assertion the runtime does not verify; if the load lifecycle ever fails to populate one, the NRE moves from a clear annotation to a runtime surprise. Accepted because Scribe always populates these and the alternative (nullable + guard on every read) adds noise to dozens of hot-path reads.
  • The stack.html statement about production nullability must be reconciled when this lands (DM-1 / AC-36).

Alternatives considered

  • Per-file #nullable enable opt-in (incremental) — rejected: leaves the project in a mixed state indefinitely, contradicts the single-target-standard goal, and the measured cost is bounded enough to do in one sprint.
  • Keep JetBrains attributes alongside real NRT — rejected: two systems that can disagree; custom-coding-rules.md mandates real NRT and the attributes are unchecked at build time.
  • Blanket = null! / #pragma warning disable to clear errors fast — rejected: defeats the purpose (the compiler stops catching real nulls); explicitly forbidden by AC-11.
  • Annotate everything first, then delete reused files — rejected: wastes effort annotating WorkTypeRule.cs (36 sites) and the wrappers that ADR-0002 deletes; the sequencing in AC-1 forbids it.
