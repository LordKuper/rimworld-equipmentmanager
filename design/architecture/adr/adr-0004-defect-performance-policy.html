ADR-0004 · Defect & performance remediation policy

accepted · subsystem N/A · updated 2026-06-07
accepted subsystem: N/A ADR-0004

Context

Most audit defects are mechanical fixes that belong in the plan, not in an ADR. Two carry a genuine cross-cutting decision and are recorded here so the implementation phase does not treat them as ordinary patches:

  • C-3 — tool-stat cache key contract. ToolCache.GetStatValue(statDef, workTypeDefs) caches by statDef only, but the WorkType custom-stat value depends on workTypeDefs (via GetWorkTypesScore). Within one 24h cache window the first work-type set's score is memoized and returned for every subsequent different set, so AssignToolsForWorkTypes (one call per work type) gives all-but-the-first work type a stale score. The StatValues cache contract cannot represent a work-type-dependent value — fixing it changes the cache key contract, not just a line of code.
  • Behavioral change from defect fixes (R-C2). Fixing C-3 and C-4 (the latter via ADR-0002's RU-2 migration) changes scoring outputs, which changes weapon/tool assignment decisions players observe. This is correct behavior, not a regression, but it must not land silently.

The mechanical performance/defect items (C-12 incremental assignedByOthers set, C-13 defName-keyed rule lookup dictionary, C-5/C-6/C-7/C-8) carry no architectural decision and are left to the plan; C-5/C-7 are resolved by the ADR-0001 flip surfacing them as CS86xx.

Decision

Two cross-cutting rules for the remediation:

  1. Cache-key correctness over caching: for work-type-dependent tool stats, either key the cache entry by the composite (statDef, workTypeDefs) or do not cache the WorkType-dependent stat at all. Caching a value whose inputs are not all in the key is forbidden — correctness wins over the cache hit (C-3, AC-15). Note the composite key is a local EM concern: Common.ThingCache (adopted in RU-3) does not provide work-type-aware keying, so this fix lives in EM's ToolCache logic on top of the re-based cache.
  2. Characterize before changing behavior: any fix that shifts scoring/assignment output (C-3, and C-4 via the RU-2 migration) must be accompanied by a characterization test on the affected math before the fix lands, and the behavioral change is called out in the PR. The first-sample [v,v] assertion (C-4) and the differing-work-type-set assertion (C-3) are required tests (AC-25, AC-29).

The mechanical performance fixes (C-12, C-13) are mandated by their own AC (AC-19, AC-20) and need no decision here beyond "do them"; they are referenced for completeness, not re-decided.

Consequences

Positive

  • Tool scores become per-work-type correct; the silent stale-score class of bug is closed at the cache-contract level, not patched per call-site.
  • Behavioral shifts are captured by tests and disclosed, so reviewers and the maintainer can distinguish "intended correctness change" from "regression".
  • Keeps the ADR corpus lean: only the two items with real decision content are recorded; mechanical fixes stay in the plan (Simplicity Default).

Negative

  • A composite cache key (or no-cache carve-out) for WorkType stats slightly raises tool-cache cost or key complexity versus the (incorrect) single-key cache. Accepted: correctness is non-negotiable and the work-type set is small.
  • Requiring a characterization test before each behavioral fix adds up-front test effort, and the post-fix assignment output will differ from prior saves' expectations (players may notice different picks). Accepted and disclosed.

Alternatives considered

  • Fold C-3 into ADR-0002 (consolidation) or leave it purely plan-level — rejected: C-3 is an EM-local cache-contract decision that survives the RU-3 migration (Common's ThingCache has no work-type keying), so it deserves its own recorded contract rather than being buried in the consolidation or treated as a one-line patch.
  • Manufacture separate ADRs for C-12 / C-13 — rejected: they are mechanical optimizations with no tradeoff to decide (Simplicity Default forbids ADRs with no decision content); they remain plan tasks under AC-19/AC-20.
  • Skip characterization tests and just ship the fixes — rejected: scoring changes are player-visible; without before/after tests a real regression would be indistinguishable from the intended correctness change (R-C2).
